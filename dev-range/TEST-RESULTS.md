## What the live checks demonstrated

- The analyst and victim shared mission LAN `10.60.1.0/24`; C2 and goal shared
  adversary LAN `10.80.1.0/24`. These were VXLAN exercise LANs over the new VPC.
- Kali reached victim SSH and goal SSH. Actual password authentication originated
  through Kali using an SSH forwarding stream: the provided victim password
  worked, the goal rejected an incorrect password, and its correct password worked.
- Victim-to-C2 mTLS worked. Sliver's actual registry showed `mission_telemetry`,
  victim address `10.60.1.20`, the deployment's victim hostname and `svc-mission`.
- Kali's `mirror0` saw live traffic between victim `10.60.1.20` and C2
  `10.80.1.10:443`. Both automated pcap capture and a browser-operated Wireshark
  session confirmed this.
- C2 SSH and Sliver's operator API were blocked from Kali. The victim could not
  reach goal SSH. Tested paths to the management underlay, original pilots,
  cloud metadata and arbitrary Internet egress were blocked.
- The operator API listened only on `127.0.0.1:31337`; the implant listener
  listened only on exercise address `10.80.1.10:443`.

The implant was generated by the official SHA256-pinned Sliver **1.7.9** release
with `--skip-symbols --debug`. It was an inspectable Linux ELF at
`/var/lib/mission/.cache/telemetry/mission-agent`, running as `svc-mission`
through the ordinary `mission-agent.service`. Its SHA256 for this deployment was
`201e66fdf8d6adc5268a270b259e3595380899c8d548907e1c03f8ad576794ca`.
The mTLS transport uses TLS over TCP 443; it is not an HTTP application protocol.

## Issues corrected during the test

- Corrected nftables rule syntax and added validation before applying it.
- Preferred Git OpenSSH on Windows after the system host-key scanner failed
  negotiation with current Kali. Host pins remain strict after first contact.
- The first new analyst lost connectivity while a broad desktop package set was
  installing. The precise cause could not be confirmed. With explicit operator
  approval, only new analyst `618674278` was replaced by `618681095`. The final
  recipe uses lean XFCE and prevents NetworkManager from taking cloud NICs.
  No original pilot was replaced or repaired.
- Created the Wireshark group explicitly because the minimal Kali installation
  did not create it automatically; configured dumpcap capabilities for analyst use.
- Set Sliver helper subprocesses' working directory to the service home. An
  unprivileged client inherited inaccessible `/root` and crashed during startup.
  The corrected helper passed with the pinned release unchanged.
- Corrected the beacon assertion for Sliver's lowercase name normalization.
- Added applied-firewall validation, partial-deployment cleanup checks, retained
  diagnostics and provider-side removal verification to the lifecycle wrapper.
- The first teardown reported provider deletion timeouts for four Ubuntu VMs.
  A fresh provider read showed all five new VMs were already absent. Re-running
  the guarded `destroy` refreshed that drift and removed the remaining new SSH
  key, tag and VPC. Final verification checked all 14 originally owned IDs.
  No manual state removal or raw cloud deletion was used.

## Evidence and limits

Private evidence is retained in ignored `.runtime/evidence/`: successful Ansible
and verification logs, all 28 results, the implant manifest, RDP fingerprint/log,
automated mirror pcap, browser capture pcapng and browser-playtest record.
The browser screenshots are in the task conversation. Cloud state, baseline,
ownership and teardown/audit reports are also retained in `.runtime/`.
No implant executable or C2 operator credential was downloaded to Windows.
The final cloud audit checked the four original Droplets, two VPCs, three
firewalls, original project, original SSH key and six images/snapshots. Their
recorded stable configuration fields were unchanged. The temporary Guacamole
connection had already been removed before cloud teardown.

This is a staff infrastructure prototype. It does not implement the scored C2
collection/recovered-credential path, goal exploitation content, credential
rotation/tripwires, per-team flags, team scheduling, or timed admission. Staff
authentication checks used prototype credentials. Those challenge mechanics can
be added to the working network and role playbooks.

The successful analyst was configured from a fresh replacement VM. The other
four new VMs were configured incrementally while fixes were developed. A second
complete fresh-fleet deployment and full-machine reboot test were not performed.
The C2 service restart was tested explicitly. Kali package repositories remain
rolling, while Terraform, the provider, Ansible and Sliver versions are pinned.
